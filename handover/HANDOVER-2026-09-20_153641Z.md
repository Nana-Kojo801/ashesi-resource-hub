# Ashesi Resource Hub — Handover

**Timestamp:** 2026-09-20 15:36:41 UTC
**Repo:** github.com/Nana-Kojo801/ashesi-resource-hub (private)
**Current `main`:** fully client-rendered Vite + React SPA (switched from the original Astro static site after an A/B test — see "Key decisions" below)

## What this project is

A static/client directory of official Ashesi University student resources (portals, forms, bookings, offices, emergency numbers), searchable by name or by intent (e.g. "my hostel AC is broken"), with anonymous flagging of broken/wrong resources. Content is edited via a Telegram bot that writes directly to this repo's YAML files through the GitHub Contents API.

## Current stack (main)

- **Vite + React + TypeScript**, fully client-rendered (no server-rendered/prerendered HTML — see "Known limitation" below)
- **React Router** (`createBrowserRouter`) for client-side routing
- **Content**: one YAML file per resource in `src/content/resources/` (74 active resources) — still the single source of truth. `scripts/build-data.mjs` reads them at build/dev time, filters to `status: active`, and emits `public/data/resources.json`, which the SPA fetches at runtime. That same script also generates `public/sitemap.xml` and `public/robots.txt`.
- **Fuse.js** client-side search (aliases weight 0.5, title 0.3, description 0.2, threshold 0.35)
- **Skeleton loaders** on every view that fetches data client-side (home board, category page, resource detail, search box) — shared `<Skeleton />` primitive in `src/components/Skeleton.tsx`
- **GSAP** for scroll-reveal/hover motion, re-triggered on route change
- **Convex** — scoped only to the `reports` (flags) table and the Telegram bot's HTTP actions; never stores resource content
- **Telegram bot** (Convex HTTP action → OpenAI function-calling → GitHub Contents API) as the only content-editing path
- **Netlify** for hosting (static `dist/` output), **pnpm** exclusively for all install/dev/build commands

## Key decisions made this session

1. **Astro → full client-side SPA.** The project was originally built per spec as Astro (static output) + Svelte islands. After reports of slow navigation, root-caused it to a render-blocking Google Fonts `<link>` (fixed on the Astro version too, ~2.1s of blocking time per PageSpeed Insights). Separately, the owner asked for a full-client-side variant to compare. Built it on `experiment/full-client-spa`, A/B tested both live on mobile — SPA navigation felt meaningfully faster with only a marginal cold-load cost — and merged it into `main` via PR #1. The Astro implementation still exists in git history (pre-merge `main`, and the branch `claude/new-session-rz9j19`) if ever needed for reference.
2. **Contacts and emergency numbers modeled as ordinary resources**, not a separate collection — categories `"Offices & People"` and `"Emergency"`.
3. **No faculty contact records imported** — none have a publicly listed email, and the source inventory explicitly forbids fabricating one.
4. **Repo made private** after initially being created public by mistake — confirmed fixed.
5. **Deployment target is Netlify**, not Cloudflare Pages (the original spec said Cloudflare; changed per owner's request early in the build).

## Known limitation (flagged, not yet acted on)

The SPA is **fully client-rendered** — a crawler or bot that doesn't execute JavaScript (most non-Google crawlers, and chat link-preview bots) only ever sees an empty shell, not real resource content. A `sitemap.xml`/`robots.txt` were added so Google at least knows every URL exists, and Google's own crawler does render JS, but less reliably/quickly than prerendered HTML would. This was an explicit, informed tradeoff for navigation speed — revisit only if search visibility becomes an actual problem (e.g. by adding prerendering back for content routes).
